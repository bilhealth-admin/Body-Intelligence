# تدقيق خصوصية وبيانات متجر Apple — 14 أكتوبر 2026

هذا تقرير قراءة فقط عن بيانات App Store Connect التي فُحصت مباشرة، ومقارنة تلك البيانات بمسودة محلية مرشحة لـ iOS 1.0.0 build 36. لا يثبت التقرير أن build 36 بُني أو رُفع أو اختُبر.

## النتيجة المباشرة

- الإصدار الذي رُفض هو **1.0.0 (build 35)**. أحدث قرار ظهر في App Store Connect كان بتاريخ 14 أكتوبر 2026، تحت **Guideline 5.1.2(i) — Legal — Privacy — Data Use and Sharing**. قالت المراجعة إن بيانات App Privacy تعلن تتبع المستخدم، ومنها **User ID وDevice ID وProduct Interaction**، بينما التطبيق لا يطلب إذن App Tracking Transparency؛ وطلبت تصحيح الإفصاح إذا كان التطبيق لا يتتبع.
- القيم الحية وقت الفحص: **أربعة اشتراكات ومنتج AI Boost الاستهلاكي كلها Ready for Review**. ملاحظة `MISSING_METADATA` السابقة قديمة ولا تصف الحالة الحية التي شوهدت.
- مرشح build 36 غير جاهز للتقديم. يذكر [سجل التجهيز المحلي](../release/BIL_IOS_V36_FROZEN_SOURCE_MANIFEST_2026-10-14.md) أن `STAGING_MANIFEST_COMPLETE: NO` و`CANDIDATE_FROZEN_OR_ACCEPTED: NO`، ولا يوجد فيه IPA موقع أو رفع TestFlight أو جلسة مراجع أو اختبار جهاز.
- لم تُغيّر بيانات App Store Connect أو الأسعار أو المنتجات أو الخصوصية، ولم يُقدّم إصدار للمراجعة. لا يحتوي هذا التقرير على بيانات دخول أو أسرار.

## مشكلة الخصوصية وما يمكن إثباته

في صفحة App Privacy الحية، كانت Privacy Policy URL هي `https://www.bilhealth.com/privacy` ورابط خيارات الخصوصية `https://www.bilhealth.com/account-deletion`. وأظهرت معاينة الخصوصية أن User ID وDevice ID وProduct Interaction معلنة على أنها **Tracking**، مع أغراض استخدام تشمل وظائف التطبيق والتحليلات أو تخصيص المنتج وإعلانات الطرف الثالث بحسب نوع البيانات.

في مصدر `e27a58984bff50b4bcf45044ea9893f344307e85`، يعلن `ios/Runner/PrivacyInfo.xcprivacy` `NSPrivacyTracking=false` وقائمة نطاقات تتبع فارغة؛ كما أن أنواع User ID وDevice ID وProduct Interaction في الملف معلنة كمجموعة مرتبطة وغير مستخدمة للتتبع، لغرض وظيفة التطبيق. ويحدد المصدر `google_mobile_ads` بالإصدار المحلول 9.1.0، ويستخدم طلبات إعلانات غير مخصصة وGoogle UMP، ويعطّل `SameAppKey` في بوابة الإعلانات. لم يظهر في البحث المصدرّي طلب ATT أو وصول مباشر إلى IDFA.

هذا الاختلاف **ليس وحده إثباتًا كافيًا لتعديل إجابات App Privacy**: الـSDK قد يجمع بياناته بنفسه. توضح وثائق Google أن الإعلانات غير المخصصة لا تستخدم معرّفات الإعلانات للاستهداف، لكنها قد تستخدمها لتحديد التكرار والتقارير المجمعة؛ كما تسرد إفصاحات SDK أنواعًا مثل معرّف الجهاز والتفاعلات والأداء وعنوان IP. لم يُربط في هذا التدقيق تقرير خصوصية Xcode مجمّع أو artifact build 35/36 بسلوك SDK الفعلي. لذلك لا نستنتج أن إلغاء أعلام التتبع وحده يعالج الرفض، ولا أن إضافة ATT مطلوبة، قبل تدقيق مسار البيانات في النسخة المعنية.

حدود النسبة مهمة: فحص المصدر أعلاه يخص SHA الحالي عند التدقيق، وليس binary build 35 الذي رُفض. ولا توجد binary build 36 لإثبات أن إجابات الخصوصية أو الإصلاحات تنطبق عليه.

## حدود App Store Connect API والخطوة الآمنة

لم تتوفر في هذه المهمة بيانات اعتماد API معتمدة أو أداة ASC API متصلة. راجعت التوثيق العام لـApp Store Connect API ولم أجد موردًا موثقًا لإجابات أنواع البيانات أو أعلام التتبع في استبيان App Privacy. توثق Apple إدارة إجابات الخصوصية عبر واجهة App Store Connect، وتطلب احتساب ممارسات شركاء SDK والإبقاء على الإجابات دقيقة ومحدثة. لم أستخدم مسارات API غير موثقة ولم أعدّل الإجابات عبر الواجهة.

الخطوة الآمنة قبل التقديم: ثبّت مصدر الإصدار المرشح وراجع ممارسات جمع البيانات للـSDK على artifact المحدد؛ بعد ذلك يراجع صاحب الصلاحية استبيان App Privacy في واجهة Apple الموثقة، ويطابقه مع نتيجة التدقيق. أنشئ أو حدّث نسخة 36 وبياناتها بعد أن تصبح حقيقية ومكتملة، ثم تحقق من أوصاف ومدة وأسعار الاشتراكات وAI Boost وملاحظات المراجعة على النسخة نفسها. لا يُعلن حل 5.1.2(i) قبل هذا الإثبات.

أُعيد فحص أدوات الجلسة وأسماء متغيرات البيئة فقط: لا يوجد موصل App Store Connect ضمن الأدوات المتاحة، ولم تظهر متغيرات اعتماد ASC/API. لم تُقرأ قيم أسرار أو تُطبع. لذلك لم يُنفّذ أي طلب قراءة أو كتابة على ASC اليوم، ولم يُرسل `PATCH` أو تعديل أو إرسال للمراجعة. لا تتوفر معرّفات API للحقول أو قراءة Before/After جديدة؛ تبقى قيم الحقول الحية المذكورة أعلاه من فحص ASC في 14 أكتوبر، ولا ينبغي وصفها بأنها قراءة حية جديدة بتاريخ 15 أكتوبر. تعذر تحديث الحقول بسبب غياب قناة API المعتمدة، لا بسبب رفض أو عطل في قيمة بعينها.

أُعيد فحص المصدر المحلي دون تشغيل اختبارات أو تغيير ملفات التطبيق: بقي `HEAD` على `e27a58984bff50b4bcf45044ea9893f344307e85`، والـworktree غير نظيف. يظل `google_mobile_ads` محلولًا إلى 9.1.0؛ المصدر يرسل `nonPersonalizedAds: true`، ويتحقق من UMP قبل طلب الإعلان، ويعطّل `SameAppKey`، بينما Privacy Manifest يعلن `NSPrivacyTracking=false`. هذه مراجعة مصدر فقط؛ لا تثبت محتوى SDK المجمع في build 35 أو artifact 36 ولا تحسم وحدها إجابات App Privacy. لم يُغيّر أي حقل ASC، ولذلك لا يوجد فرق Before/After أو Field ID لتسجيله.
